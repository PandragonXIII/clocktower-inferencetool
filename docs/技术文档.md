# 技术文档：血染钟楼推理助手

本文面向技术评审，说明当前代码实际实现的范围、架构、数据流、推理语义与已知限制。项目只支持《血染钟楼·暗流涌动》5–15 人普通局，不包含旅行者、其他剧本和完整的胜负判定。以下描述以仓库当前实现为准；规则细节参考公开 wiki，第三方依赖与授权见[第三方资源说明](第三方资源说明文档.md)。

## 1. 总体架构与数据流

系统由四层组成：

```text
浏览器原生 HTML/CSS/JS
        │  POST /api/v1/reason（完整快照）
        ▼
backend/http_server.py（Python 标准库 http.server）
        │  validation.py 运行时校验
        ▼
connector.TroubleBrewingAdapter（JSON ↔ 模型桥）
        │  declare_variables + rules + compile_inputs
        ▼
botc_reasoner/（直接使用 z3-solver 的暗流涌动约束模型）
        │  pipeline.analyze / probability_adapter / repairs / worlds
        ▼
JSON 响应（consistency、查询结果、冲突、扩展结果）
```

- `web/` 是原生 JavaScript 静态页面，不使用前端框架，也没有 CDN 运行依赖。
- `backend/` 基于 Python 标准库 `http.server`，同源提供 `web/` 静态文件与 `/api/` API；负责请求体限制、JSON 解析、运行时校验和 HTTP 错误映射。
- 根目录 `connector.py` 是网页协议与 Z3 模型之间的桥，也是实际运行求解器的适配器入口。`main.py web` 注入 `TroubleBrewingAdapter`；只有直接调用 `create_server()` 且不传 adapter 时才使用 placeholder。
- `botc_reasoner/` 是本项目唯一的推理模型，直接把规则写成 Z3 约束，没有额外的通用推理引擎抽象层。

一次请求的数据流是：前端把当前圆桌、记录、假设和查询组装成完整 JSON；后台校验字段形状、稳定 id、引用和时间；连接器把命题映射为变量表达式并编译输入；`pipeline.analyze` 分别求解 public 与 conditional 两条轨道；最后把一致性、逐查询状态、冲突依据、参与说明和可选扩展写回响应。

`main.py` 提供 `test`、`demo`、`web` 三个子命令，没有 `engine` 或 `winrate` 子命令。仓库另有 `botc_reasoner/engine.py`（前向结算辅助）与 `botc_reasoner/winrate.py`（胜率估计命令行工具），二者有独立测试，但不接入 `main.py` 子命令和网页 API，也不属于网页推理主链。`winrate` 可用 `.venv/bin/python -m botc_reasoner.winrate <局面.json>` 单独运行；`engine.py` 也不是第二个 Z3 推理模型，不改变 `botc_reasoner/` 作为网页唯一 Z3 推理模型的定位。仓库当前没有跟踪的通用 `engine/` 包，保留的 `botc_reasoner/engine.py` 是具体的暗流涌动前向结算器；它不改变网页以 `botc_reasoner` 直接 Z3 建模为主的架构，也不能据此认为网页另有一套通用推理引擎。

## 2. 无状态请求、稳定 id 与旧响应防护

`POST /api/v1/reason` 是无状态接口：每次请求携带完整的 `game`、`facts`、`assumptions`、`queries` 和可选 `options`，服务端不保留会话。这样前端可以自由撤销、停用和重算，不需要同步服务端状态。

`request_id`、`game.id`、`player.id`、`fact.id`、`assumption.id`、`query.id` 都是稳定 id，并在同一请求内跨集合共享命名空间，重复即拒绝。`game.revision` 必须是非负整数；命题时间不得晚于 `game.time`。响应回显 `request_id`、`game_id`、`revision`；前端同时使用异步 epoch 和这三项标识拒绝旧响应，避免较慢的旧请求覆盖新快照。

`enabled` 是记录参与推理的唯一开关；旧字段 `requested_enabled` 仅作兼容，不会复活已停用记录。停用的扩展记录可以保存未完成草稿，后台不解析其 `data`。

逻辑矛盾与 HTTP 错误严格分开：`consistency:"unsat"` 是正常推理结论，返回 200；格式、引用、类型或未知活跃类型等错误返回 4xx，并带 `code`、`message` 和 JSON Pointer `path`。前端不会把 HTTP 错误显示成逻辑矛盾。

## 3. 输入语义：两轨、来源与 belief

输入按 `scope` 只分两条推理轨道：

- **public**：默认只有 `confirmed` 的夜间死亡公布和 `stage:"settled"` 的白天投票/处决。其他记录若要成为 public，必须显式设置 `reasoner:scope:"public"`，且事实必须为 `confirmed`。
- **conditional**：其余启用事实与假设。`reported` 永远不能升级为 public；假设只能是 conditional。

public 轨道由规则和公共输入组成；conditional 轨道在 public 基础上加入其他启用输入。顶层 `results` 对应 conditional，`reasoner:scopes` 同时保留两轨。public 背景矛盾时该轨道查询返回 `inconsistent`，不能用矛盾前提推出任意命题。

`confirmed` 与 `reported` 是来源标记，不能简单等同于“真实”与“自认”两个维度：

- `reported` 的 `role` 命题映射为**自认身份 belief**，即该玩家认为自己是什么角色，不是真实身份。酒鬼的自认可以与真实身份不同。
- `confirmed` 的 `role` 命题映射为真实角色。当前 `reported` 的 `alignment` 仍直接约束真实阵营，这是现有语义边界，不应理解为完整的“声明阵营 belief”模型。
- `reasoner:source` 只用于展示与修复追溯，不构成第三类可信等级；`owner_id` 用于概率分组和修复代价，也不是真假轴。
- `enabled` 是唯一参与开关；`status` 说明来源，`scope` 说明推理轨道，三者互不替代。

只有 `reported` role 被映射为 belief，`confirmed` role 不会被静默降级；scope 分类与“映射真实命题还是 belief”是两件独立的事。

## 4. Z3 规则模型

`roles.py` 定义 22 个官方角色、5–15 人配置表 `BASE_SETUP`、男爵修正与角色目录；`variables.py` 声明身份、自认、存活、中毒/醉酒、夜间行动、死亡、提名和投票变量，并加入“每名玩家每断面恰好一个角色”等域公理；`rules.py` 把配置、开局秘密、身份延续、夜间击杀、中毒/醉酒、信息技能、提名投票和处决写成 Z3 约束。`provenance.py` 只记录约束对应的规则组来源，便于冲突诊断引用。

时间使用 `setup`、`night k`、`day k`，内部另有 `NIGHT_START`、`DAWN`、`AFTER_LAST_DAY` 断面。首夜没有恶魔击杀；僧侣、小恶魔、守鸦人、送葬者等从第 2 夜开始。投票模型允许自提名和提名死者，提名者必须存活；死者整局最多投一票。后端 Z3 约束用严格超过半数（票数 `>= (alive_count+1)/2`）判定处决；前端默认选择值用 `Math.ceil(alive_count/2)` 展示并允许手动覆盖，两者在偶数存活人数时会相差一票，前端展示值不替代后端约束。

已建模的规则包括男爵配置、酒鬼标记、占卜师干扰项、恶魔三个不在场伪装、中毒/醉酒、夜间击杀与僧侣/健康士兵保护、小恶魔自杀后的星坠、红唇女郎转化、猎手、贞洁者、投票处决，以及健康角色收到的部分信息，包含间谍/陌客的逐次误注册。

模型仍有时序和范围限制，技术评审不应把“结构可提交”理解为“完整规则已验证”：

- 尚未建模圣徒处决落败、镇长三人获胜等完整游戏结束条件；连接器只转换可观察到的部分约束，不判断胜负。
- 同一天多个死亡、处决与角色转化的精确事件顺序不能完整表达；当前是阶段断面模型。投毒者被星坠成为恶魔后“立即停止中毒”的细时点也未完整建模。
- 同一白天重复提名的先后、提名槽上限和部分白天死亡顺序仍受模型限制；前端保存的违规记录不会因此变成有效规则。
- 间谍魔典文本、陌客未指定事件的备注、疑似镇长转移等自由文本不会被解析成隐藏真相。
- 模型只覆盖暗流涌动，没有旅行者、其他剧本，也没有把“输入结构可接受”等同于“该角色所有组合都已建模”。

## 5. 一致性与查询

`pipeline.analyze` 先构建变量、规则和编译后的输入，再分别检查 public 与 conditional 背景：

- `sat`：存在满足全部约束的模型。
- `unsat`：当前启用输入与规则不能同时成立。
- `unknown`：预算耗尽或单次求解超时。

每条查询分别尝试命题及其否定：

| 正向 | 反向 | 状态 |
| --- | --- | --- |
| `sat` | `sat` | `possible` |
| `sat` | `unsat` | `necessary` |
| `unsat` | `sat` | `impossible` |
| 背景 `unsat` | — | `inconsistent` |
| 任一方向 `unknown` | — | `unknown` |

`unknown` 是保守结论，不能向上取整成可能、必然或不可能，也不能把未命中的角色读成不可能。

矛盾诊断把域公理、每条规则组、每条输入分别作为 gate，取不可满足核后做 inclusion-minimal 收缩。`minimality:"inclusion"` 只表示核内任一 gate 都不能再删除，**不是最小基数冲突集**；预算不足时为 `"unverified"`。诊断报告的是“哪些输入与规则组不能同时成立”，不是事件级、步骤级的证明链。旧字段 `conflicts` 同样是规则组和输入级依据。

可选扩展只在有条件时执行：

- `reasoner:repairs`：条件背景 `unsat` 且 `max_repairs>0` 时搜索撤回方案，public 输入固定不可撤，先最小化变更 owner 数再最小化撤回条数；每个候选都在剩余完整问题上重新验证 `sat`。达到数量或检查上限时，最优代价与方案列举完整性分别标注，未完成不能当作不存在修复。
- `reasoner:worlds`：`sat` 且 `max_worlds>0` 时枚举初始角色的联合世界，按全体玩家的联合投影去重；只有 `complete:true` 时 `total` 才是精确计数。达到 `max_worlds`、预算耗尽或求解 `unknown` 时截断，并标注 `truncated_reason`。`total` 只是计数，不是概率，也不表示各世界等可能。
- `reasoner:role_ranges`：逐玩家检查初始角色可行性，把角色分为可行、已排除和未判定；预算耗尽时未判定角色保留，不误当排除。该扩展在概率模式下被跳过，以把预算留给概率估计。

`reasoner:participation` 按每条输入返回 `applied`、`partial`、`record_only` 或 `disabled`，说明它是否被编译成约束；`applied` 不代表该约束一定可满足。

## 6. 概率估计

概率是**可选的带权抽样估计**，不是精确概率，也不是逻辑结论的替代品。开关为 `options.probability_mode`，结果写入 `extensions["reasoner:probabilities"]`；默认关闭。它的 `scope` 固定为 `conditional`，`time` 固定为 `{"phase":"setup"}`，只估计初始身份，不是第三条推理轨道，也不改变 public/conditional 的逻辑结果。

当前适配器 `probability_adapter.analyze_probabilities` 的语义：

1. **public 输入是硬条件**：每个组合的求解器都包含全部 public 输入。public 背景 `unsat` 返回 `status:"inconsistent"`，不抽样；public `unknown` 返回 `unknown`。
2. **conditional 输入是软条件**：按 `owner_id` 分组，没有归属的输入各自成组。每组以可信度 `0.7` 做伯努利采信，生成“采信/忽略”组合，组合权重为 `0.7^采信组数 × 0.3^忽略组数`。
3. **组合覆盖**：组数不超过 6 时全枚举 `2^n` 种；超过 6 时用固定种子 `0` 抽至多 64 种，并包含全采信与全忽略两个极端组合。此时 `groups.complete` 为 `false`，只覆盖部分组合。部分覆盖本身仍可能返回 `estimated`，但未覆盖的组合既不能当作已排除，也不能据此宣称概率完整。
4. **矛盾组合**：conditional 输入之间矛盾只让相应组合不可满足并被跳过，剩余一致组合继续估计并归一化，结果仍可为 `estimated`。只有 public 背景矛盾才是 `inconsistent`。
5. **抽样参数**：每个可行组合调用核心 `estimate_role_probabilities`；该函数内部复用 `joint_assignment_particles` 的联合权重与样本。当前 `probability_adapter.py` 的实际常量是 `seed=0`、`target_accepted_per_group=2`、`max_trials_per_group=16`，不是“每组尝试 4 次”。这是压低网页交互耗时的有界覆盖，样本很少；数值以代码当前常量为准。
6. **未知处理**：组合检查或抽样因预算耗尽、单次求解超时或未取到样本而中止时，返回 `unknown`、`rows:[]`，且不归一化只成功的部分组合；不能把缺失读成零概率或不可能。
7. **完整性**：`complete` 恒为 `false`；组合覆盖另见 `groups:{total,checked,estimated,complete}`。`estimated` 不是精确概率，没有置信区间或误差界；抽样也不保证各身份等概率或采样均匀。
8. **与逻辑结果独立**：概率模式不改变 `consistency` 与 `results`。概率模式下 `pipeline.analyze` 跳过 `diagnose` 与 `role_ranges`，但显式查询、`max_repairs`、`max_worlds` 和真实 `unsat` 结论仍保留。

适配器只构建一次“变量域公理 + 规则 + public 输入”的 solver，每个采信组合用 `push()`/`pop()` 临时加入该组合的 conditional 表达式；组合之间不重建求解器，规则和 public 背景也不会重复加载。

核心估计器 `probability.py` 还按“采信人数、忽略人数、信息写法数、投毒/酒鬼/红鲱鱼/陪衬”等乘数加权，在可行组内抽样后归一化。命令行工具 `test_reasoning.py` 仍按玩家可信度把自认与技能声明分为软采信组；HTTP 适配器的分组键是通用 `owner_id`，且 public 输入始终是硬条件，两者输入组织不同，不应直接比较同名百分比。

## 7. 预算与超时

当前代码的默认值与边界（以工作区最新实现为准）：

| 选项 | 默认 | 范围 | 作用 |
| --- | --- | --- | --- |
| `timeout_ms` | 1000 | 正整数 | 每次 Z3 solve 的上限 |
| `total_timeout_ms` | 8000 | 1..60000 | 整段逻辑分析共享的总预算 |
| `probability_timeout_ms` | 120000 | 1..300000 | 概率估计独立的总预算 |
| `max_worlds` | 0 | 0..100 | 初始世界枚举上限，0 关闭 |
| `max_repairs` | 0 | 0..10 | 撤回方案数量上限，0 关闭 |
| `max_repair_checks` | 128 | 1..1024 | 每类修复搜索的求解次数上限 |

`Budget.check` 每次取“总预算剩余”和 `timeout_ms` 的较小值作为 Z3 timeout。逻辑分析与概率估计使用两个独立 `Budget`；概率预算不占用 `total_timeout_ms`。预算只覆盖分析阶段的求解，不包含变量声明、规则收集、建模构建、适配器锁等待和 HTTP 传输，因此是软预算而不是 HTTP 硬截止。适配器用单把锁串行化请求，排队时间也不计入任何阶段。

前端传输超时由 `requestTimeoutMs` 动态计算：逻辑总预算（默认 8000，上限 60000）加概率预算（仅开启概率时，默认 120000，上限 300000）再加 30000 毫秒宽限；最大为 390000 毫秒。`timeout_ms` 是单次求解上限，不累加进传输超时。

**预算口径核对**：本仓库当前 checkout 与 `origin/main`/`origin/UI`/`origin/Engine` 中，连接器的概率默认值是 `120000`（与 `types.ts` 一致），校验上限 `300000`，逻辑分析默认 `8000`；不存在“连接器默认 6000、文档默认 3000”的当前实现。本机另有一个未进入 Git 历史的旧工作树 `/tmp/opencode/engine-base-20261018-132016`，其中是连接器概率默认 `6000`、`types.ts` 默认 `3000`、校验上限 `30000`，前端固定 `20000` 毫秒超时；这些旧值彼此也不一致，不能拿来描述当前代码。若其他成员的分支仍显示 `6000`，说明该分支未合并到当前 HEAD，演示前应先与 `main` 对齐。

按当前前端公式，概率关闭时等待 `8000 + 30000 = 38000` 毫秒（38 秒），开启概率时等待 `8000 + 120000 + 30000 = 158000` 毫秒（158 秒）。若仍套用旧的概率默认 `3000`，同一公式会得到 `8000 + 3000 + 30000 = 41000` 毫秒（41 秒）；这是旧默认值对应的结果，不对应当前代码。当前校验范围是 `1..300000`，旧基线的 `30000` 上限不适用于当前代码。部署和演示时应在 `options` 中显式写出 `total_timeout_ms`、`probability_timeout_ms` 和 `timeout_ms`，不要依赖跨分支可能不同的默认值；本文按当前实现记录，不为了文档叙述修改代码。

## 8. 网页与接口约定

网页只依赖同源 API，`main.py web` 同时提供静态页面和 `/api/`。接口约定：

- `GET /api/v1/capabilities` 返回支持的输入类型、查询类型、剧本和适配器模式；真实适配器的 `adapter:mode` 为 `trouble_brewing`。
- `POST /api/v1/reason` 接收完整快照，校验后调用适配器。请求体要求 `application/json` 和单个 `Content-Length`，上限 1 MiB；拒绝重复 JSON 键、`NaN`/`Infinity` 和 `Transfer-Encoding`。
- 未知且活跃的扩展类型必须拒绝；四类已知扩展为 `botc:ability_observation`、`botc:night_deaths`、`botc:day_vote`、`botc:global_assumption`。结构或引用错误返回 400，结构合法但当前模型不支持的组合返回 422。
- 前端通过 `enabled` 控制记录是否参与；未结算投票以停用草稿保存，结算后启用。身份声明保持 `reported`，不会自动升级为真实身份。

一个最小合法的 5 人请求可以很短：玩家用列表给出，`facts` 和 `assumptions` 可以为空，只保留一个查询。例如：

```json
{
  "api_version": "1.0",
  "request_id": "req-min-1",
  "game": {
    "id": "game-min-1",
    "revision": 0,
    "script_id": "trouble_brewing",
    "players": [
      {"id": "p1", "seat": 1, "name": "1号"},
      {"id": "p2", "seat": 2, "name": "2号"},
      {"id": "p3", "seat": 3, "name": "3号"},
      {"id": "p4", "seat": 4, "name": "4号"},
      {"id": "p5", "seat": 5, "name": "5号"}
    ],
    "time": {"phase": "setup"}
  },
  "facts": [],
  "assumptions": [],
  "queries": [
    {"id": "q1", "proposition": {"kind": "alignment", "player_id": "p1", "alignment": "good", "time": {"phase": "setup"}}}
  ],
  "options": {"total_timeout_ms": 3000, "timeout_ms": 1000}
}
```

发送方式：

```sh
curl -sS http://127.0.0.1:8000/api/v1/reason \
  -H 'Content-Type: application/json' \
  --data @request.json
```

也可直接运行连接器求解同一份 JSON：

```sh
python connector.py request.json
```

该命令行路径**不经过** `backend.validation`，非法输入可能得到 `unknown` 或异常；HTTP 路径才会先做运行时校验。

## 9. 部署与运行

运行依赖只有 `z3-solver>=4.13.0`，Python 使用标准库 `http.server`，前端为原生 JavaScript。安装与启动：

```sh
python -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python main.py web --host 127.0.0.1 --port 8000
```

浏览器访问 `http://127.0.0.1:8000/`。`main.py` 的默认端口参数当前为 8001（见 `DEFAULT_PORT`），但帮助文本仍写 8000；部署时建议显式传 `--port`，避免依赖默认值。

其他入口：

```sh
# 运行测试
.venv/bin/python main.py test
# 运行最小推理演示（不启动服务）
.venv/bin/python main.py demo
# 兼容入口，行为等价于 main.py web
.venv/bin/python connector.py serve --port 8000
# 只提供静态页面，不含 API
python -m http.server 8000 --bind 127.0.0.1 --directory web
```

前端测试使用 Node 内置测试运行器：

```sh
node --test web/tests/*.test.cjs
```

## 10. 测试、原创与边界

测试按模块组织在 `tests/`，覆盖协议校验、HTTP 传输、输入分类、规则回归、冲突诊断、修复、世界枚举、概率适配器和入口分发；前端测试覆盖记录交互与请求超时计算。具体用例以当前测试文件为准，本文不声称固定用例数量。模拟对局记录在 `tests/simulate-games/`，它们是人工主持的规则对照材料，不是推理引擎输出，也不作为能力验证。

原创范围包括前端交互、Python 标准库 HTTP 服务、协议校验、连接器桥接、暗流涌动 Z3 约束建模、冲突诊断、修复搜索、世界枚举和概率适配。规则细节参考公开的[血染钟楼官方 wiki](https://wiki.bloodontheclocktower.com/)与[钟楼百科](https://clocktower-wiki.gstonegames.com/)，未复制其代码或资源；依赖与授权见[第三方资源说明](第三方资源说明文档.md)。

主要限制再归纳如下：

- 只支持暗流涌动 5–15 人，不包含旅行者、其他剧本和完整胜负判定。
- 冲突解释是规则组与输入级依据，不是逐步证明，也不是最小基数冲突集。
- 概率是启发式带权抽样，不是精确概率，没有误差界；未采样角色不代表不可能。
- 世界枚举与修复搜索受预算和数量上限约束，完整性需看各自的 `complete`/`optimality` 字段。
- 网页未展示全部高级扩展；`reasoner:scopes`、`reasoner:diagnosis`、`reasoner:repairs`、`reasoner:worlds`、`reasoner:role_ranges` 等可直接查看 API JSON，但不能据此宣称界面已提供对应可视化。前端当前展示的是 `reasoner:participation`、`reasoner:probabilities`、顶层冲突和 `trouble_brewing:possible_roles`。
- `engine.py` 与 `winrate.py` 是仓库内的独立辅助模块，未接入网页 API，也未接入 `main.py` 子命令。
